NexusFlow — Full Technical Defense Report

NexusFlow is a production-grade, OS-level security appliance built on a Java 21 / Netty data plane, Spring Boot control plane, and React NOC dashboard. It intercepts, analyzes, and manipulates every packet at the OS level — with no browser extensions, no kernel modules, and no cloud dependency.

System Design

Two-Plane Architecture

NexusFlow separates packet processing (data plane) from configuration and monitoring (control plane). The data plane never touches the database; the control plane never touches raw packets. Communication happens through a reactive event bus.

┌─────────────────────────── OS KERNEL LAYER ───────────────────────────┐
│ Wintun TUN Driver ──→ all IP traffic captured at ring-0, zero-copy
└───────────────────────────────────────────────────────────────────────┘
↓ JNA bridge (wintun.dll)
┌─────────────────────── DATA PLANE (Netty event loop) ─────────────────┐
│ RawIpPacketHandler → QuicInterceptionHandler → SentinelIdsHandler
│ → BeaconDetectorHandler → AegisFilterHandler → ExfiltrationGuardHandler
│ → GhostShardEncoder → ProtocolPolymorphismEncoder → StreamShatterHandler
│ → DeepTraceHandler → ShieldFabricHandler → ProcessSandboxHandler
│ → RelayHandler → upstream
└───────────────────────────────────────────────────────────────────────┘
↓ ForensicsEvent bus (Project Reactor)
┌─────────────────────── CONTROL PLANE (Spring Boot) ───────────────────┐
│ REST APIs · WebSocket forensics feed · H2 DVR store · Policy DSL engine
└───────────────────────────────────────────────────────────────────────┘
↓ WebSocket /ws/forensics
┌─────────────────────────── REACT NOC DASHBOARD ───────────────────────┐
│ Overview · IRONCLAD · IDS/IPS · AEGIS · Counter-Score · DVR · Policy
└───────────────────────────────────────────────────────────────────────┘
Key principle: The data plane (Netty) never touches JPA, HTTP, or Spring. The control plane never handles raw bytes. This separation guarantees that forensics events and API calls never contend with packet processing on the Netty event loop.

All 15 Active Security Features

Every feature operates inline — packets pass through a Netty ChannelPipeline where each handler either passes, transforms, or drops the traffic. There is no out-of-band copying or port-mirroring.

Feature 1 — Project IRONCLAD OS-Level
Zero-Config TUN Virtual Adapter Interface

What it does

IRONCLAD creates a virtual network adapter named "NexusFlow" at the OS level using JNA (Java Native Access) to load WireGuard's wintun.dll — the same driver that powers WireGuard VPN on Windows. It then modifies the OS routing table to redirect 100% of all outbound IP traffic through this adapter, regardless of which application generated it.

How it works

Raw IP packets flow from the kernel's ring buffer directly into Java via the JNA bridge, wrapped into Netty ByteBufs, and fed into the pipeline. A Java 21 virtual thread loop (not an OS thread) continuously reads from the Wintun ring buffer at near-kernel speed. On non-Windows platforms, a simulation mode generates synthetic IPv4/TCP packets for testing.

Feature 2 — ALPN & QUIC Hardening UDP/443
Force HTTP/3 → HTTP/2 Fallback via QUIC Drop

What it does

HTTP/3 runs over QUIC (UDP port 443). Because QUIC is encrypted end-to-end from the first byte, it cannot be inspected for threats, ads, or exfiltration. This handler silently drops QUIC UDP packets, forcing the browser (Chrome, Firefox, Edge) to fall back to standard TLS 1.3 over TCP within ~100ms — which CAN be analyzed.

Detection logic

QUIC Initial packets are detected by:

// RFC 9000 Long Header fingerprint
Byte 0: 0x80–0xFF // Long Header bit set
Bytes 1–4: 0x00000001 // QUIC Version 1
0xFF00001D // Draft-29
0xFACEB002 // Facebook MVFST
ALPN scan: 0x68,0x33 // "h3" byte sequence

Features 3, 4, 5 — Anti-Censorship & Evasion Triad
GHOST-SHARD · STREAM-SHATTER · DECEPTICON

GHOST-SHARD (Feature 3) — Anti-DPI

A MessageToMessageEncoder that slices outbound TCP payloads into randomized byte fragments with three size distributions:

  • 50% small chunks: 12–127 bytes
  • 40% medium chunks: 128–847 bytes
  • 10% full remaining payload

Between fragments, cryptographic noise frames (magic 0xDEAD + random bytes) are interleaved. A TLS ClientHello — which has a recognizable 5-byte header at offset 0 — becomes unrecognizable binary noise when spread across 8 fragments at random offsets.

STREAM-SHATTER (Feature 4) — Anti-Tap

Injects "ghost packets" into the outbound TCP stream. Each ghost frame carries a 0xCAFEBABE magic header and one of three types:

  • Type 0x01 — overlapping sequence numbers
  • Type 0x02 — intentionally bad TCP checksum
  • Type 0x03 — out-of-order frame clone

NexusFlow-aware receivers strip ghost frames. Passive wire-tap devices try to reassemble the stream and fail catastrophically.

DECEPTICON (Feature 5) — Protocol Mimicry

Wraps tunnel traffic in one of three trusted protocol shapes: RTP video stream (fake WebRTC with plausible SSRC/timestamp), DNS TXT records (base64 payload in synthetic DNS responses), or WebSocket frames (RFC 6455 binary frames). DPI classifiers see whitelisted protocols.

Features 6 & 7 — Project SENTINEL-IDS + Beacon Detector Wire-Speed
Embedded Local NIDS/NIPS + EWMA Behavioral Analysis

SENTINEL-IDS — How it works

The IDS engine builds an Aho-Corasick finite state automaton from all loaded threat rules. This is the same algorithm used by Snort and Suricata. It scans a byte stream for ALL patterns simultaneously in a single O(n) pass — no matter how many signatures are loaded, each byte is examined exactly once.

// Scanning is O(n) — linear in packet size,
// NOT O(n×m) like naive string matching
for (i = offset; i < end; i++) {
state = go[state][text[i] & 0xFF];
if (output[state] != -1) // match!
result.add(new Match(...));
}

When a rule matches with action DROP, the Netty channel is immediately closed. LOG rules add an alert to the ring buffer and forward traffic.

Beacon Detector (Feature 7)

Tracks connection intervals per remote host using an EWMA scoreboard. A host connecting at exactly 30-second intervals produces near-zero interval variance — score approaches 1.0. When score ≥ 0.75, the connection is terminated and flagged.

score = 1.0 − min(1.0, variance/interval)
// Score → 1.0 = perfect beacon cadence
// Score ≥ 0.75 → DISCONNECT + ALERT

Features 8 & 9 — SAFE-ZONE + SHIELD-FABRIC
Process Sandbox + Anti-Mirroring Line-Tap Sentinel

SAFE-ZONE (Feature 8) — Process Sandbox

Maps every TCP connection to its originating PID via /proc/net/tcp (Linux) or GetExtendedTcpTable (Windows). Each PID is assigned a trust level:

  • TRUSTED — full network access
  • UNTRUSTED — ports 80, 443, 53, 5353 only
  • SANDBOXED — all external connections blocked

An unknown background script that tries to connect to port 8443 is immediately terminated if its PID is in UNTRUSTED mode. The process continues running — it just can't reach the internet.

SHIELD-FABRIC (Feature 9) — Tap Detection

Measures the round-trip time between writes and the first inbound data for each connection. An EWMA tracks the baseline RTT. If RTT spikes by more than the 3-sigma threshold:

  • Delta > 50ms → INTERFACE_MIGRATE (switch lane)
  • Delta > 20ms → CIPHER_ROTATE (new session keys)
  • Otherwise → ALERT_ONLY

A passive tap splitter adds a constant latency offset (typically 2–40ms depending on the splice hardware). SHIELD-FABRIC detects this as an anomalous sustained RTT shift and triggers countermeasures.

Features 10, 11, 12 — AEGIS + BLACK-HOLE + Exfiltration Guard
OS-Wide Ad Block · Telemetry Sinkhole · Data Theft Prevention

AEGIS (Feature 10) — Radix Trie Blocklist

Stores 1.8M+ domain entries in a lock-free Radix Trie where labels are indexed in reverse (TLD → subdomain). This means:

  • Lookup is O(k) — k = number of domain labels
  • Wildcard blocking: blocking "doubleclick.net" auto-blocks ALL subdomains
  • Concurrent reads are completely lock-free — ConcurrentHashMap per node
  • No GC pressure on lookups — pure pointer chasing
// "ads.doubleclick.net" lookup:
root → ["net"] → ["doubleclick"] ✓ TERMINAL
// Returns: blocked=true, category=ADVERTISING
// Never reaches "ads" node — wildcard match!

BLACK-HOLE (Feature 11) — Telemetry Sinkhole

Instead of just blocking telemetry connections, BLACK-HOLE intercepts the TCP stream and returns a synthetic HTTP 200 OK response with an empty JSON body {}. The reporting app believes it successfully phoned home, stops retrying, and goes to sleep. This prevents battery-draining retry storms and saves data.

Exfiltration Guard (Feature 12)

Features 13, 14, 15 — DEEP-TRACE · COUNTER-SCORE · Nexus Guide
Off-Heap Forensics · XKeyscore Dashboard · Interactive Tour

DEEP-TRACE (Feature 13) — Off-Heap Ring Buffer

Allocates 512 direct ByteBuf slots (4096 bytes each = 2 MB total) as off-heap memory using Netty's UnpooledByteBufAllocator. This means zero GC involvement — no matter how many packets are recorded, the Java garbage collector never sees them.

Each new connection's first 512 bytes are written into the ring. If a threat is later flagged on that connection, the exact bytes that preceded the alert are instantly available as a structured diagnostic block — no disk I/O, no file reads.

Capacity: 512 slots
Slot size: 4,096 bytes
Total: 2 MB (off-heap, direct)
GC allocs: 0 on hot path
Lock model: StampedLock optimistic reads

COUNTER-SCORE (Feature 14) — XKeyscore Dashboard

A live forensics grid that groups all network flows by Process ID. For every running application, it shows:

  • PID & process name — from OS process table
  • Bytes in/out — formatted MB/GB
  • Blocked requests — AEGIS + IDS blocks
  • Active connections — live socket count
  • Threat score — composite 0.0–1.0 (visual bar)
  • Protocol list — HTTPS, WSS, QUIC→HTTP2, etc.

The threat score formula: high outbound-to-inbound ratio (potential exfil), regular beacon cadence, and presence on the IDS alert list all increase the score. A score >0.9 (like suspicious_bg.exe) triggers an amber warning indicator.

Alongside the process table, a live AEGIS block rate area chart and protocol morphing action counters (GHOST-SHARD, DECEPTICON, STREAM-SHATTER) show the current system load in real time.

Where does the data come from?

Data Sources — No External Runtime Calls

This is the most important architectural point: NexusFlow makes zero external API calls at runtime. All threat data, blocklists, and GeoIP databases are downloaded once at startup or loaded from local disk. Every lookup, every scan, every block decision happens entirely in local memory.

On the "47,000+ signatures" number: The current build ships with 10 hard-coded built-in rules. The 47K target is achieved by loading the Emerging Threats Open ruleset (free, from Proofpoint) at startup. The Aho-Corasick automaton rebuilds atomically — adding 47,000 rules adds zero per-packet overhead because the scan is still O(n) regardless of pattern count.

How to load Emerging Threats rules (47K signatures)

The ET Open ruleset is free and publicly available. To load it into SENTINEL-IDS:

# Download ET Open rules (free, updated daily)
wget https://rules.emergingthreats.net/open/suricata-6.0/emerging.rules.tar.gz
tar -xzf emerging.rules.tar.gz

# SentinelIdsEngine will parse .rules files at startup
# Each rule's content: field is extracted as the byte pattern
# Aho-Corasick automaton is built atomically — one swap, zero downtime

The Aho-Corasick trie build time for 47,000 patterns is approximately 800ms at startup. After that, per-packet scan time does not increase — it's always O(n) where n = packet bytes inspected.
